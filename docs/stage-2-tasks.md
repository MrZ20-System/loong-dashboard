## Frozen decisions

### D1. Tables (migration 004)

`pull_request_files`, `domain_rules`, and `pull_request_domains` are created
exactly as already declared in `packages/database/src/schema.ts` (Stage 0
froze the shapes; only the migration was missing). One additive column is
added to `pull_requests`:

- `files_truncated INTEGER NOT NULL DEFAULT 0` — set when GitHub reports more
  than 3000 files for one PR head (plan 9.6; V1 does not resolve further).

### D2. Domain rule contract

- `DomainRule { id, repositoryId, name, color, position, enabled,
  includePatterns, excludePatterns, createdAt, updatedAt }`.
- `color` is `#rrggbb`; the server assigns a palette color when omitted.
- `name`: trimmed, 1-40 chars, unique per repository (DB constraint).
- `includePatterns`: 1-50 patterns; `excludePatterns`: 0-50 patterns.
- Create body: `{ name, color?, includePatterns, excludePatterns, enabled? }`.
- Update body: any subset of the same fields; at least one field required.
- `position` is assigned by the server (`max(position) + 1`); no reorder API
  in V1.

### D3. Domain rule API (plan 17.3)

```text
GET    /api/repositories/:id/domains
POST   /api/repositories/:id/domains
PUT    /api/repositories/:id/domains/:domainId
DELETE /api/repositories/:id/domains/:domainId
```

- GET returns `{ items, reclassification: { running, pendingCount } }`.
- Mutations return `{ item, reclassification }` (DELETE returns
  `{ deleted: true, reclassification }`). The reclassification snapshot lets
  the web show "重新分类中" without a second endpoint.
- Rule ids are `dom_<random>` generated by the server (crypto).
- Unknown repository → `REPOSITORY_NOT_FOUND` (404); unknown domain id →
  `DOMAIN_NOT_FOUND` (404); duplicate name → `DOMAIN_NAME_CONFLICT` (409).

### D4. Classification semantics (plan 10)

- Paths are normalized to `/` separators, leading `./` stripped.
- A rule matches a file when any include pattern matches AND no exclude
  pattern matches (picomatch, `dot: true`).
- One matching file is enough to attach the domain to the PR; a PR can carry
  multiple domains; no primary domain, no confidence, no AI.
- `classificationKey = sha256(ruleSetHash + "\n" + fileSetHash)` per PR.
  - `ruleSetHash`: sha256 of the JSON of enabled rules' `{id, include,
    exclude}` sorted by id. Renames/recolors do not change it.
  - `fileSetHash`: sha256 of the sorted current-head file paths.
- If the stored key equals the computed key, rows are left untouched.

### D5. Changed file enrichment (plan 9.6)

- A PR needs enrichment when no `pull_request_files` row exists for its
  current `head_sha` (covers new PRs, head changes, and previously failed
  enrichments).
- Provider method `fetchPullRequestFiles({ repository, pullRequests })`:
  batches of up to 20 node ids via GraphQL `nodes(ids:)` with
  `files(first: 100)`; when a PR reports `hasNextPage`, fall back to the REST
  `repos/{owner}/{repo}/pulls/{number}/files` endpoint with `per_page=100`
  pagination; stop at 3000 files and mark `files_truncated=true`.
- At most 2 batches run concurrently (plan 9.8 budget).
- `changeType` is normalized to lowercase (`added`, `modified`, `removed`,
  `renamed`, `copied`, ...). GraphQL `CHANGED` maps to `modified`.
- After files for a PR are replaced, rows for stale head SHAs of that PR are
  deleted; classification for that PR is recomputed locally.
- Enrichment runs after the PR metadata stream succeeds. Its failure is
  logged and does NOT fail the metadata stream; affected PRs are retried on
  the next sync (plan 9.9).
- When the metadata stream reports `rateLimitRemaining` below 200, enrichment
  is skipped for this round (metadata wins; documented constant).

### D6. Reclassification after rule CRUD (plan 10.3)

- One serial in-process background task per repository; no queue package.
- Triggered by every successful rule mutation; never calls GitHub.
- Processes PRs that have file rows in batches of 200, recomputing D4 keys.
- If a mutation arrives while a run is active, exactly one follow-up run is
  scheduled (dirty flag).
- `{ running, pendingCount }` is exposed through the domains GET response.

### D7. PR list domains (plan 17.2, 18.1)

- `GET /api/repositories/:id/pulls` accepts repeated `domain` query params
  (`?domain=a&domain=b`); a single value is also accepted. Semantics: ANY —
  a PR matches when it carries at least one selected domain.
- `PullRequestListItem` gains `domains: [{ id, name, color }]` ordered by
  rule position. The list query stays SQLite-only; chips are loaded with one
  batched IN query for the returned page.
- `GET /api/repositories/:id/pulls/:number/files` returns the stored current
  -head file rows `{ headSha, truncated, items }` (404 when the PR is
  unknown; `items` empty when enrichment has not run yet).

### D8. Web

- PR list rows render domain chips; the toolbar gains a multi-select domain
  filter (only on the pulls page); selections live in the URL as repeated
  `domain` params.
- New `/settings/domains` page: repository selector, rule list, create/edit
  form (name, color, include/exclude patterns one per line, enabled), delete,
  and a reclassification-in-progress indicator polled while running.
- The PR list shows a small "重新分类中" hint while reclassification runs.

## Stage 2 acceptance (plan section 27)

- A PR touching `.github/**` hits the CI rule.
- One PR can carry multiple domains.
- Rule mutations never call GitHub.
- An unchanged `head_sha` never re-fetches files.
- `pnpm check` passes; the deferred Stage 1 real-GitHub smoke remains
  honestly reported as deferred.

## Explicit non-goals for Stage 2

- No reorder API, no domain analytics, no Issue classification.
- No routine browser E2E harness. Browser-level domain coverage is an explicit
  manual acceptance activity.
- No AI anywhere in classification.
